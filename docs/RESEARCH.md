# Standalone course-planning viability

**Verdict:** A standalone site can unify course discovery, public schedules, historical grades, professor links, and a student-imported degree plan. It cannot reliably replace authenticated Schedule Builder seat data, Howdy's personalized audit, or registration. The best fit is both: a standalone planning hub, plus an optional browser extension that reads only the signed-in user's visible Schedule Builder page. Keep registration in Howdy. Do not collect SSO credentials, automate enrollment, or treat public open/closed flags as seat counts.

## 1. Sections and seats

- **Public source works, with a major limitation.** On 2026-11-05, an unauthenticated `POST https://howdyportal.tamu.edu/api/course-sections` with the supplied body (`startRow:0`, `endRow:0`, `termCode:202711`, `publicSearch:"Y"`) returned HTTP 200. It returned 20,649 sections in a 32,559,839-byte response. The response `Date` was 17:51:56 UTC. The endpoint has no public contract or documented refresh SLA that I found. One full response took about 17.5 seconds from this environment. The official [public class search](https://howdyportal.tamu.edu/uPortal/p/public-class-search-ui.ctf1/max/render.uP) is the supported user-facing source; [AggieCourses](https://github.com/jasenio/AggieCourses) documents hourly syncing of section data from the public Howdy API.
- **Seat accuracy is not measurable from this public response.** For the nine requested CRNs in the supplied watch data, `SWV_CLASS_SEARCH_SEATS_AVAIL`, max enrollment, enrollment, and waitlist fields were all `NA`. `STUSEAT_OPEN` was `Y` for eight and `N` for CSCE 435 section 500. The local watch snapshot had numeric seat estimates from a Nov 3 Schedule Builder check, but was not rechecked; the public response was newer by about 3h46m and had no numeric counts to compare. `Y/N` is an open-status signal, not a seat count. No public numeric capacity or near-live seat source was verified.
- **Schedule Builder remains an authenticated source.** The university links [Aggie Schedule Builder](https://howdy.tamu.edu/main/home/card-info/64), and its separate [College Scheduler app](https://tamu.collegescheduler.com/entry) displays live section availability in the student's session. I found no documented public feed or supported cart-import API. I did not sign in or inspect authenticated traffic, so the vendor's underlying source and refresh interval remain unknown. Do not infer that it reads a particular Banner endpoint.

## 2. Grades, RMP, and matching

- **anex.us:** The public site describes historical grade distributions by course and instructor ([Anex grades](https://anex.us/grades/)). The requested JSON POST to `https://anex.us/grades/getData/` (`dept=CSCE`, `number=412`) did not reach the application: HTTPS connection was refused from this research environment, including a retry to `www.anex.us`. I could not verify response schema, endpoint uptime, rate limits, or terms. No rate policy or API license was located. Treat it as a useful but uncontracted dependency, not a guaranteed API. Texas A&M's [Registrar grade reports](https://registrar.tamu.edu/registration-scheduling-and-analytics/data-and-analytics/grades-report) are an official fallback; the Registrar describes reports as point-in-time data for the five most recent years.
- **RMP:** One read-only POST to `https://www.ratemyprofessors.com/graphql`, searching school ID `U2Nob29sLTEwMDM=` and `Robert Lightfoot`, returned HTTP 200. The first matching Computer Science result was 3.2 / 127 ratings. The query also returned other results, including a same-name professor with a different department and no ratings. This shows the undocumented GraphQL endpoint works technically, not that it is a supported or licensed data feed. No rate limit is published in the sources checked; one request cannot establish a safe limit.
- **Important licensing risk:** RMP's [Terms of Use, sections 4 and 6](https://www.ratemyprofessors.com/terms-of-use) reserve site material and prohibit automated access, scraping, crawling, or spidering without express prior permission. They also restrict reproduction and redistribution. Do not fetch, cache, or republish RMP data without written permission. A safe default is a user-clickable RMP link; any ratings integration needs permission and a review of current terms.
- **Instructor identity is fuzzy.** Public section data gives display-name strings, not a stable instructor ID. Names may include initials, middle names, suffixes, or teaching-role markers; RMP search can return homonyms. Match by school plus normalized first/last name and department where available, show rating count and source link, and leave ambiguous/unmatched results unbadged for manual confirmation. Never silently assign a same-name rating.

## 3. Registration boundary

No documented CRN deep link or public cart import was found. A standalone planner can produce a conflict-free schedule and a copyable CRN list, then link students to Howdy or Schedule Builder. Keep the final review and registration action in those official services. Until TAMU documents an import interface, a CRN paste list is the only safe, supportable handoff identified here. A browser extension may display or link to information in the open Schedule Builder page, but must not automate registration or move credentials/session data to the site's server.

## 4. Existing tools

- [AggieCourses](https://github.com/jasenio/AggieCourses) is a working standalone course-search project. Its README describes hourly public-Howdy section refreshes, and its repository includes public section snapshots, restrictions, and grade-distribution data. It says schedule building is a planned addition. This is direct evidence that public data supports a useful search product, not live private seats.
- [Aggie Schedule Builder Plus](https://aggieschedulebuilderplus.vercel.app/) already advertises course search, grade data, professor insights, seat alerts, and a Chrome extension for registration-page context. Its [Firefox listing](https://addons.mozilla.org/en-US/firefox/addon/aggie-schedule-builder-plus/) also describes professor ratings and grade distributions. These are product claims, not independent verification of source freshness or licensing. Check product ownership, data permissions, and naming before duplicating it.
- [Aggie-Registration-Alert](https://github.com/aggie-coding-club/Aggie-Registration-Alert) is an older open-source alert site; its README says it alerts when filled courses become available. [AggieSeek](https://aggieseek.net/landing) and [AggieClassAlert](https://www.aggieclassalert.com/help) also advertise seat monitoring. Their public pages establish prior art, but do not document an authorized live-seat feed. Do not assume they have a supported API or that their scraping approach is permissible.

## 5. Degree plan, audit, and privacy

### Public requirements versus private progress

The [2026-27 undergraduate catalog](https://catalog.tamu.edu/) exposes public course descriptions, program pages, plan-of-study tables, and catalog-year archives. For example, the [Computer Science BS](https://catalog.tamu.edu/undergraduate/engineering/computer-science/bs/) publishes a plan grid, hours, required choices, and program notes. These pages can seed a versioned requirements graph. They are not the student's personalized audit and do not encode completed/transfer coursework, advisor decisions, or all operational department rules. Keep catalog year and source on every rule, and mark ambiguous/elective mappings for advisor confirmation.

The [Undergraduate Degree Planner student guide](https://www.tamug.edu/advising/pdf/DegPlan.pdf) says UGDP is accessed in Howdy, supports a term-by-term plan, a degree evaluation, prerequisite checks, templates, and plan approval. It documents printing planned courses to PDF. The guide is older and campus-hosted; confirm current College Station UI before relying on specific buttons. In the current workflow reviewed for this research, UGDP and degree audit are distinct: a degree evaluation is a snapshot against the selected program/plan, approval state belongs to the plan, and registration holds/action items are separate. No structured API or machine-readable audit export was found. A student can use an official print/PDF view where offered, or paste/export their own plan and completed-course list; automated parsing should preview every inferred requirement for confirmation.

Requirements should feed section choice through versioned buckets and constraints: required course groups, electives/tracks, minimum grades, prerequisites, transfer equivalencies, course attributes, and section-specific flags. Associate a planned course with every applicable bucket, but distinguish confirmed audit matches from suggestions. Section number, CRN, and any planner checkbox can matter, so course-code-only matching is insufficient. A useful planner would expose what requirement a course may satisfy and why, count prior/transfer credit only when the student confirms it, surface separate Holds/Action Items, and flag rules that need advisor or departmental confirmation. This addresses tool switching, stale personal spreadsheets, section/campus traps, audit-versus-advising discrepancies, and easily missed registration blockers without pretending to be the official degree audit.

### FERPA and handling

The [U.S. Department of Education FERPA FAQ](https://studentprivacy.ed.gov/frequently-asked-questions) defines education records and explains that an outside provider receiving records under the school-official exception must perform an institutional function, remain under the institution's direct control, and meet use/redisclosure limits. A student's own voluntary import into an independent app is not automatically the same as TAMU outsourcing a function; the exact legal status depends on how the service is operated. Degree audits, grades, transfer work, and advisor comments are sensitive student-linked data. Prefer local-only import/storage, collect no NetID or password, do not upload the PDF by default, provide deletion, and obtain privacy/legal review before server-side storage or TAMU integration. See also TAMU's [FERPA Compliance Rule 16.01.02.M1](https://rules-saps.tamu.edu/PDFs/16.01.02.M1.pdf) and [Information Resources Acceptable Use SAP 29.01.03.M0.02](https://rulesadmin.tamu.edu/rules/download/29.01.03.M0.02), which requires respecting resource owners and avoiding disproportionate or unauthorized use.

## 6. Recommendation and hard problems

Build a **standalone hub plus optional extension**, not a Schedule Builder replacement:

1. Standalone Rust-backed service: import public sections on a conservative schedule; index term/campus/attributes; build schedules; ingest official historical grades where terms allow; link to RMP until written data permission exists; allow student-controlled local UGDP/audit PDF or pasted data; keep requirement rules catalog-year-versioned and visibly uncertain.
2. Thin browser extension: only with explicit opt-in, read visible seat/status details from the user's already-open Schedule Builder page and link its selected sections back to the planning hub. Do not relay cookies, scrape hidden endpoints, bypass SSO/Duo, or submit registration. Confirm College Scheduler and TAMU terms before shipping.
3. Official handoff: show CRNs and a Howdy/Schedule Builder link. User completes registration there.

Hardest problems are lawful and reliable live-seat access, RMP permission, UGDP/audit parsing and keeping degree rules aligned with catalog year/advising practice, and avoiding false instructor or requirement matches. Resolve those with TAMU/College Scheduler data agreements, written RMP permission, and user-reviewed imports. Until then, a standalone site can consolidate planning but cannot truthfully claim live availability or official graduation progress.
